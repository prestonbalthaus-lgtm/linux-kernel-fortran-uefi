# Roadmap 6.2: the filesystem driver

6.1 ended with a promise: `vfs_lookup` is the one seam, an ops table would be
indirection with a single entry, and `s_priv`/`i_priv` are declared for the
block number a filesystem will want. This is that promise kept. A cache miss
now means "read the directory off the NVMe drive", and nothing above it changed
shape to allow that.

## The four decisions

### 1. ext2, and the deciding reason is the seam rather than taste

`vfs_lookup` compares `(LENGTH, BYTES)` -- `dcache.h`'s `dentry_cmp` -- and FAT
stores short names uppercased and matches them case-INSENSITIVELY. A FAT driver
must therefore either fold case *inside* that comparison, changing what the seam
means for everyone, or implement long-name reassembly to recover a byte-exact
name. ext2 names are byte-exact on disk and drop into the existing compare with
nothing added.

Three lesser reasons, in order:

- FAT32 is not legally FAT32 below 65525 clusters. The gate's fixture is 1 MiB
  and `qmp-sentinel.py`'s `IMAGE_BLOCKS` is 2048; FAT32 would take it past
  33 MiB.
- ext2's root is inode 2, a CONSTANT (`ext2.h:162`). FAT32's root is a cluster
  chain to be walked from the boot record.
- The constants oracle is already in the tree. `fs/ext2/ext2.h` is what
  `test_vfs.c` does with the uapi headers, one directory over.

### 2. One disk carries both milestones

ext2 reserves its first 1024 bytes for a boot block and puts its superblock at
byte 1024 (`super.c:933-937`). Roadmap 5.3's prologue at 0, its `55AA` at 510
and its `FORTRAN-KERNEL!!` at 512 all live inside that reserved space, so every
assertion 5.3 makes about sector 0 still holds byte for byte. The generator
asserts the boot block is untouched before splicing them back.

### 3. The oracle is e2fsprogs, and that is the point

`tools/gen-ext2-oracle.sh` builds the fixture with `mke2fs` and reads the
expected inode numbers, sizes and block numbers back with `debugfs`.
`qmp-sentinel.py` gained an INDEPENDENT ext2 walker in Python. Three readers of
the same bytes must agree, which is roadmap 4.1's standard: a parser and a
formatter written by one hand can share a misconception and agree with each
other.

The LAYOUT has its own oracle: the four on-disk structs are CUT VERBATIM out of
the vendor's `ext2.h` by `gen-ext2-oracle.sh`, and every offset the driver uses
is diffed against `offsetof` over them. `ext2.h` cannot simply be included --
it pulls in `linux/fs.h`, `linux/mm.h` and `linux/highmem.h`.

Three of those offsets have an in-tree oracle of their own worth naming:
`ext2.h:610-617`'s `verify_offsets()` is a `BUILD_BUG_ON` that `s_magic`,
`s_blocks_count` and `s_log_block_size` sit at 0x38, 0x04 and 0x18.

### 4. The block seam is resolved by the linker, not by a table

`src/fs/fk_blkdev.f90` declares `fk_blk_submit` and does not define it.
`fk_blkdev_nvme.f90` defines it for the kernel and `tests/fs/test_ext2.c`
defines it over a `mke2fs` image. Neither knows the other exists. It is the
identical arrangement `fk_readl`/`fk_writel` already have with `boot/io.S`, and
it is why the ext2 parser the host suite exercises is byte for byte the parser
that runs on the metal.

`fk_ext2.f90` therefore never holds an address at all.

## The refusals are dir.c's

`ext2_check_folio` (`dir.c:118-131`) makes five checks on a directory record,
and the driver makes the same five in the same order. The first is the one that
matters most:

| refusal | dir.c | what it prevents |
|---|---|---|
| `rec_len < EXT2_DIR_REC_LEN(1)` | :122 | an offset that never advances -- the walk does not answer wrongly, it never answers |
| `rec_len & 3` | :124 | a length no `EXT2_DIR_REC_LEN` could have produced |
| `rec_len < EXT2_DIR_REC_LEN(name_len)` | :126 | a name read out of the NEXT record's bytes |
| the record spans the block | :128 | a walk past the end of what was read |
| `inode > s_inodes_count` | :130 | an entry naming an inode the table cannot hold |

A corrupt entry ABANDONS THE BLOCK rather than skipping to the next record:
once a `rec_len` is untrustworthy there is no next record to skip to, because
the offset that would find it came from the field that just failed.

## What is deliberately not here

TWELVE DIRECT BLOCKS AND NO INDIRECTION. `i_block[0..11]` is 12 KiB at a 1 KiB
block, which covers every directory the gate builds and the init stub in one.
It does NOT cover a real BusyBox. Roadmap 6.4 writes the singly-indirect block;
a file this driver cannot reach is REFUSED with `-EFBIG` rather than silently
truncated, which is the difference between a known debt and a discovered one.

READ-ONLY, structurally. No write path means no allocation bitmap is consulted
and no free count updated, which is what lets `s_state` refuse a dirty
filesystem outright instead of replaying anything, and what makes ignoring
every `ro_compat` bit correct rather than lazy.

## Two defects found in other people's boxes

**Roadmap 5.3's completion wait was too short.** Its 2,000,000-iteration spin
expired in 3 of 31 boots, only ever on a host running back-to-back VMs -- an
empty spin measures host CPU time, not device time, and under KVM a contended
vCPU is descheduled while the device is still working. It surfaced as
`FK_NVME_E_CMD`, the controller blamed for a completion that had not arrived.
0 of 14 at 200,000,000. The boot gate had never been run a dozen times in a row
before, so it was latent rather than absent.

**A diagnostic that named the wrong mechanism cost an hour.** `ext2_bringup`
reported its own steps as -1..-4, which collides with `fk_ext2.f90`'s -1..-14,
so an unreadable superblock and a missing buffer said the same thing. The
allocator was investigated for a fault it did not have. The ranges are disjoint
now (-100..-104) and the device timeout count prints next to every failure.
