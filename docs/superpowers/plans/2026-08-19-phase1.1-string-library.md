# Roadmap 1.1: the string half

1.3 paid the MEMORY half of this box -- memset, memcpy, memmove, memcmp,
translated from vendor `lib/string.c` and diffed against it. The STRING half
has been owed since Phase 1 and `roadmap.md:239-243` says what it blocks: 6.1's
path resolution and 6.4's ELF loader, neither of which can start without it.

## Measured before anything was written

`mk/string.mk` selects functions out of the vendor file with that file's own
`__HAVE_ARCH_*` guards. Dropping four of those defines and compiling:

    strcpy   strcmp   strncmp   strlen      <- the four wanted
    memset   memcpy   memmove   memcmp      <- 1.3's, already there
    sized_strscpy  stpcpy  strnchrnul  memchr_inv   <- unguarded, already there

zero warnings, **zero undefined symbols**. So the whole oracle side of this
milestone is four deletions from one variable. No new shim, no new fragment, no
new harness -- exactly what the roadmap box predicted.

The second measurement is the one that could have changed the design.
`fk_string.f90`'s header claims gcc's loop-distribution pass cannot recognise a
`c_f_pointer` loop, so the intrinsics cannot recurse into themselves. That was
measured for a **fill/copy** loop. GCC also has an idiom recogniser for
**exit-on-sentinel** loops -- the `strlen`/`rawmemchr` shape -- which is a
different pattern and has never been measured in this tree. If it fires, the
`strlen` in `fk_string_abi.f90` calls itself and the kernel hangs on its first
path lookup.

Measured on gfortran 16.1.1, all four functions, three flag sets:

| build | undefined symbols |
|---|---|
| `FFLAGS` (`-O2 -fwrapv`) | none |
| `KFLAGS` (the real kernel set) | none |
| `-O3 -ftree-loop-distribute-patterns` explicitly on | none |

No `strlen`, no `rawmemchr`, no `_gfortran_*`. The claim in the header holds for
this shape too, and it is now measured rather than extended by analogy.

## The three decisions

### 1. The descriptor's extent is not a length limit

`c_f_pointer` needs a shape and C's pointer arithmetic does not, and that is the
entire difference between the two languages here. A string's length is not known
until the terminator is found, so the shape is `huge(0_c_int32_t)` and the
contract stays C's, unchanged: the object must be NUL-terminated, and an
unterminated one walks off the end in both implementations. Nothing is
allocated; a Fortran array descriptor is three words and a base address.

### 2. `strcmp` and `strncmp` return -1, 0 or 1 -- not a difference

`lib/string.c:35` is `return c1 < c2 ? -1 : 1`, which is NOT what `memcmp` two
functions above it does. The C standard only requires the sign, so an
implementation returning `c1 - c2` is a conforming `strcmp` and a **failing
translation**: the differential test compares the exact `int`.

The comparison is also on `unsigned char`, so `0x80` against `0x00` is `1` and
not `-1`. That is memcmp's sign trap in a new costume and it gets the same
treatment -- an explicit value table, not a random sweep that would find it
eventually.

### 3. The guard PAGE, because the guard REGION cannot see a read

1.3's arena catches a write outside `[dest, dest+n)` by diffing the whole 4 KiB
against a per-case snapshot. That is strictly stronger than a canary band and it
is blind to the failure mode that actually matters here: **reading** past the
terminator. `strlen` that scans one byte too far returns the right answer;
`strncmp` that ignores `count` returns the right answer whenever the strings
differ earlier.

So there is a second arena: two pages from `mmap`, the upper one `PROT_NONE`,
and the string planted so its terminator is the **last readable byte**. A read
one byte past it faults. A `SIGSEGV` handler and `siglongjmp` turn that into an
ordinary mismatch line instead of a dead process, so the harness still reports.

The oracle runs on the same buffer. It passing is the evidence the page is
placed where this claims it is.

`strncmp` with `count = 0` flush against the boundary is the strongest case in
the file: it asserts that **nothing at all** is read.

defines exactly the symbols the oracle object defines.

## Mutations planned

- `strlen` counts the terminator
- `strlen` reads one byte past the terminator (guard page only)
- `strcpy` drops the terminator
- `strcpy` copies the terminator and one more byte
- `strcmp` returns `c1 - c2` instead of the sign
- `strcmp` compares signed bytes (the `0x80` trap)
- `strcmp` misses the equal-and-terminated exit, running off both ends
- `strncmp` ignores `count`
- `strncmp` decrements `count` before the terminator test, off by one
- `strncmp` with `count = 0` reads a byte (guard page only)
