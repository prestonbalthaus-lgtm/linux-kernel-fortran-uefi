# Roadmap 5.3: the NVMe controller, and sector 0

4.2 finds the drive, 3.x gives it contiguous memory, `fk_nvme_types` carries the
register layouts, and 5.2 has now walked the whole PCIe-to-device path once. 5.3
is the third pillar: persistent storage, read into a Fortran array and put on the
screen.

## Measured before anything was written

Booting the current tree with `-device nvme` attached, and reading the device
model:

    00:03.0  1B36:0010  class/sub/progif 01/08/02   <- pcie_find_nvme matches
    BAR0 0x680000000, 64-bit          <- ABOVE the 24 GiB of RAM
    MSI-X cap 0x40, 65 entries, BIR 0, table 0x2000
    CAP 0x004008200F0107FF
      MQES 2048   CQR 1   TO 15 (7.5s)   DSTRD 0 -> doorbell stride 4
      MPSMIN 4096   MPSMAX 65536
    VS 0x00010400 (1.4.0)   CC 0x0   CSTS 0x0

Three of those changed the plan:

- **The PCI function set grew from six to seven and the gate stayed green.**
  4.2's `info pci` comparison is a SET on both sides, so it absorbed the new
  function without a line of change. Only qmp-sentinel's hardcoded self-test
  fixture needs the seventh entry.
- **BAR0 is above top-of-RAM.** `vmm_punch_physmap` only punches below
  `map_top` and refuses anything overlapping an AVAILABLE region, so a BAR up
  there is a correct no-op rather than a special case. Nothing to add.
- **CQR is 1**: queues must be physically contiguous. `pmm_alloc_contiguous` is
  exactly that, and it is why 3.x had to land first.

## The six decisions

### 1. The MSI-X vector is SHARED with the xHCI, and the assertion accounts for it

There is one MSI vector (0x30) and one stub line, and growing the 17-entry stub
table buys nothing: two devices on one vector is what the handler already does
for two sources. `irq_handler` calls `usbkbd_isr` then `nvme_isr`; each drains
its own device and returns having found nothing if the interrupt was not its.

That makes "an interrupt arrived" useless as an NVMe assertion, so the assertion
is not that. `fk_nvme_state` carries a counter incremented **only inside
`nvme_isr`, and only when it actually consumed a completion**. That is the
interrupt path delivering NVMe's completion specifically, and no other device
can raise it.

### 2. Enumeration polls; the handler takes the queue afterwards

Verbatim 5.2's lesson, including the ordering that got it wrong the first time:
the bring-up polls every completion, and the ISR is armed **after** the
polled phase ends, with the owner flag set before interrupts are enabled. M75
is what happens otherwise, and it will happen here identically if the NVMe ISR
drains a CQE the bring-up is waiting on.

### 3. CC is composed in full, then enabled

MPS=0 (4 KiB, matching the measured MPSMIN), CSS=NVM, **IOSQES=6 and IOCQES=4**.
Enabling with those two at zero is the failure that surfaces two commands later
as `Create I/O SQ -> Invalid Queue Size`, a long way from its cause.

CC.EN is already 0 on this model, so "clear EN, poll RDY=0" passes trivially.
It is still done, and the harness document says the disable path is
**unexercised** rather than counting it as evidence.

### 4. The admin queues are TWO entries, so the phase tag actually wraps

This is the M33 shape for this milestone. A completion queue's phase tag starts
at 1 and flips every time the consumer wraps; with a 64-entry queue and six
commands the wrap **never runs**, and a driver with inverted wrap logic passes
every gate that will ever be built.

Two entries is the specification's minimum and it makes the bring-up wrap the
admin CQ twice on its own — Identify Controller, Identify Namespace, Create CQ,
Create SQ is four commands through a two-deep queue. No artificial padding
command, and the wrap is exercised by the ordinary path.

### 5. NLB is zero-based, and the disk fixture is built to catch that

`Read` takes the block count in CDW12[15:0] **minus one**: 0 means one block.
The generated disk carries `00 01 02 ... 0f` at sector 0 and the ASCII
`FORTRAN-KERNEL!!` at sector 1, so an off-by-one LBA or a two-block read is a
different sixteen bytes rather than a plausible one. The image is **generated,
not committed** — a binary fixture in git is one nobody can read a diff of.

### 6. One PRP entry, and no PRP list

Identify returns 4096 bytes and a 512-byte read is one block, both into
page-aligned buffers, so PRP1 is the buffer and PRP2 is zero in every command
this milestone issues. A transfer crossing a page boundary would need PRP2 or a
PRP list; nothing here does, and the code says so rather than implementing an
untested path.

## Memory

One `pmm_alloc_contiguous` run of six pages, for 5.1's reason:

    +0  admin SQ    +1  admin CQ    +2  I/O SQ
    +3  I/O CQ      +4  identify buffer    +5  sector buffer

## The gate

`-drive file=…,format=raw,if=none,id=nvm -device nvme,drive=nvm,serial=fk1234`,
inside the existing `MACHINE != pc` guard.

**The sector diff reads the image file, not a hardcoded constant.** The checker
`pmemsave`s 512 bytes at the physical address the guest published and compares
them against `disk.img` on the host, so a changed fixture cannot drift away from
its own assertion.

Assertions, all from guest memory or the device model:

- CSTS.RDY set, CC.EN set, and CC's IOSQES/IOCQES as programmed
- AQA, ASQ and ACQ as the controller holds them
- the LBA size decoded from Identify Namespace, and the namespace size
- the CQE's status field, phase, and the command id it names
- **the 512 bytes, byte for byte against the host's image**
- completions consumed **in interrupt context**, which is the only NVMe-specific
  statement the shared vector permits

## Mutations planned

- CC.EN never set / RDY never polled
- IOSQES/IOCQES left zero
- AQA written with the entry count rather than count-1
- ASQ and ACQ swapped
- the phase tag never flipped on wrap
- the CQ head doorbell never rung
- NLB written as 1 rather than 0 (reads two blocks)
- SLBA 1 rather than 0 (the sector-1 signature catches it)
- PRP1 left zero
- the ISR drains before it owns the queue (M75's shape)
