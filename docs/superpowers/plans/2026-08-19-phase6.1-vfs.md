# Roadmap 6.1: the VFS

Every hardware pillar is up: 2.2 draws, 5.2 reads keys, 5.3 reads blocks. What
is missing between "sector 0 is in a Fortran array" and "run /bin/init" is a
name. 6.1 is the layer that turns a path into an object, and it is deliberately
NOT a filesystem: no ext2, no FAT32, no disk parsing. That is 6.2.

1.1 had to land first. A path is a string, and until this week there was no
strlen, strcpy, strcmp or strncmp in the tree.

## The five decisions

### 1. HANDLES INTO STATIC POOLS, not pointers into a heap

`03-guidelines.md` forbids a dynamically allocated array in a kernel module
without explicit lifecycle management, and the heap this tree has is single
threaded, not preemption safe, and stops allocating before `sched_start`. A
dentry tree that outlives bring-up cannot live in it.

So the pools are `save` arrays sized by a `parameter`, exactly the shape
`fk_nvme_m`'s `NQ` and `fk_xhci_m`'s `FK_XHCI_TR_MAX` already use, and every
link is a 32-bit INDEX rather than an address. Handle 0 is "none", which is why
the pools are 1-based.

Three things fall out and all three are the point:

- The lifecycle is explicit and testable: allocate to exhaustion, get `-ENOMEM`,
  free one, allocate again. That test is what makes the claim measured.
- There is no pointer for gfortran to narrow and nothing for `mmiocheck` to
  refuse. This module never touches a device register.
- The whole tree is one `.bss` object the host suite and the QMP sentinel can
  both read at a known symbol.

The structs are still `bind(c)` as the directive asks. An `integer(c_int32_t)`
handle is a C field; what makes them C-compatible is the layout, not the
presence of a `struct dentry *`.

### 2. Names are stored INLINE at NAME_MAX, which is a deviation with a reason

`dcache.h:72-87` gives Linux a 40-byte inline name and an external allocation
for anything longer. There is nothing to allocate from here, so a dentry carries
`NAME_MAX + 1 = 256` bytes and the limit a caller sees is the vendor's 255
rather than an implementation artifact at 40.

64 dentries is 18 KiB of `.bss`, which is `NOBITS` and costs the image no file
bytes -- `linkscript-test.sh`'s 256 KiB ceiling is a FileSiz check.

### 3. Path resolution is `link_path_walk`'s BYTE-AT-A-TIME variant

`fs/namei.c:2537-2557` is the `!CONFIG_DCACHE_WORD_ACCESS` `hash_name`, and its
loop condition is the entire separator rule:

    } while (c && c != '/');

The word-at-a-time variant above it does the same thing with
`load_unaligned_zeropad` and a `has_zero` pair, and it is the wrong model for a
scaffold: its whole content is x86 page-safety tricks for a hot path this kernel
does not have.

The semantics are taken from that function and its callers, not invented:

| input | behaviour | source |
|---|---|---|
| leading `/`, and runs of `/` between components | skipped | namei.c:2583-2587, 2635-2637 |
| `""` | `-ENOENT` | nothing to resolve |
| `"/"` | the root | namei.c:2588-2591, `last_type` stays `LAST_ROOT` |
| `"."` | stays put, a pure no-op | `handle_dots` falls to `return NULL`, namei.c:2258 |
| `".."` | the parent; at the root, the root | `follow_dotdot`'s `in_root:` label, namei.c:2217-2220 |
| trailing `/` | the result must be a directory, else `-ENOTDIR` | namei.c:2782-2783 sets `LOOKUP_DIRECTORY` |
| a non-final component that is not a directory | `-ENOTDIR` | namei.c:2662-2667 |
| a component longer than `NAME_MAX` | `-ENAMETOOLONG` | uapi/linux/limits.h:12 |
| a path longer than `PATH_MAX` | `-ENAMETOOLONG` | uapi/linux/limits.h:13 |
| no such entry | `-ENOENT` | |

**Trailing slash is not stripped.** Linux does not strip it either: the
component's length stops at the slash and the surviving byte is what
`lookup_last` tests. Stripping it during tokenisation is the one shortcut that
would silently lose `-ENOTDIR` on `open("/bin/init/")`, so the resolver carries
the flag instead.

`vfs_resolve_at(base, path)` takes a starting dentry. An absolute path ignores
it. There is no cwd in this kernel and inventing one here would be a Phase 7
decision made by accident.

### 4. NO ops tables, and the seam is named instead

The directive says scaffold the layer a filesystem driver plugs into. A
`type(c_funptr)` `inode_operations` is not that layer, it is the dispatch
mechanism for a layer that has TWO implementations to choose between, and today
there are none. M3c's argument in the other project applies unchanged.

The seam is one function -- `dentry_lookup(parent, name, len)` -- which today
walks the child list and compares `(len, bytes)`. 6.2 is the first caller that
needs a miss to mean "ask the disk", and that is where the indirection earns
itself. `s_priv` and `i_priv` are `c_int64_t` on the superblock and the inode,
which is `s_fs_info`'s job: the block number an ext2 driver stores.

Name comparison is `(len, bytes)`, which is what `dentry_cmp` does and what
tokenisation hands over for free. `strcmp` is not the right tool for a component
that is terminated by a slash rather than by a NUL.

### 5. Three constant ORACLES, and no function oracle

There is no C function to diff a VFS scaffold against -- `fs/namei.c` is
entangled with the mount table, RCU, credentials and the dcache hash, and
nothing extractable remains. `mk/serial.mk` is the precedent: a fragment with no
`ORACLE_` variable, diffed against a reference model in the test itself.

But the CONSTANTS have real oracles and the test includes the vendor headers
directly rather than transcribing them:

    asm-generic/errno.h     ENOENT ENOTDIR EISDIR ENAMETOOLONG ENOMEM EINVAL
    linux/stat.h            S_IFMT S_IFDIR S_IFREG and the permission bits
    linux/limits.h          NAME_MAX PATH_MAX

They need `-D__KERNEL__` (uapi/linux/stat.h:7 hides the mode bits from glibc)
and one empty shim, `tests/shims/vfs/linux/compiler_types.h`. Measured: that is
the whole shim set.

The ABI half has an oracle too, and it is the C compiler. The pools are
`bind(c)` arrays, the test declares its own mirrored `struct`s over the same
memory, writes through one and reads back through the Fortran accessors. A
layout disagreement is a wrong value, not a silent divergence -- stronger than
comparing `offsetof` numbers, and it needs no enumeration of field ids.

## Memory

    inodes    64 x  48 bytes  =  3072
    dentries  64 x 284 bytes  = 18176
    files     16 x  24 bytes  =   384
    supers     4 x  40 bytes  =   160

21.3 KiB of `.bss`, and the sizes are read back out of the object rather than
counted by hand: `nm` gives 0x4700 for `fk_vfs_dentries`, which is 64 x 284.
Every pool is published under a `bind(c)` name.

## Mutations planned

- `..` at the root escapes upward instead of staying
- a repeated slash produces an empty component that matches nothing
- the trailing-slash flag is dropped, so `/bin/init/` resolves
- a non-final non-directory is walked through instead of `-ENOTDIR`
- name comparison ignores the length, so `bi` matches `bin`
- `NAME_MAX` is checked as `>` rather than `>=` on the buffer
- freeing a dentry does not return it to the pool
- freeing a dentry does not unlink it from its parent's child list
- the inode's link count is not decremented on remove
- `vfs_open` for write on a directory is allowed
