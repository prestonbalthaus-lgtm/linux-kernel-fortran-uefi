# Roadmap 5.2: the USB HID keyboard

5.1 left a running controller, a command ring that wraps correctly, an event
ring and a working MSI-X route, and deliberately built the one thing that needs
none of USB. 5.2 is everything it skipped: a slot, a device context, an address,
control transfers, an interrupt endpoint, and a character on the screen.

## What is being built

1. **Port** — find the connected root-hub port, reset it, read its speed.
2. **Slot** — Enable Slot, allocate the Device Context, link it into the DCBAA.
3. **Address** — Input Context with the slot and EP0, Address Device.
4. **Configure the device** — `GET_DESCRIPTOR(DEVICE)`, `GET_DESCRIPTOR(CONFIG)`,
   `SET_CONFIGURATION`, and `SET_PROTOCOL(boot)`.
5. **EP1 IN** — Configure Endpoint, a transfer ring, Normal TRBs.
6. **Render** — decode the 8-byte boot report and put the character on the GOP
   framebuffer through `fk_console`.

## The five decisions that shape the code

### 1. Enumeration POLLS. The ISR owns the event ring only afterwards.

There is one event ring and it can have exactly one consumer. Enumeration needs
to wait for a completion after every command, and doing that inside an interrupt
handler means the handler drives USB enumeration, which is absurd for a
milestone whose only device is a keyboard.

So the interrupter's IE is **taken down for the whole of enumeration**, every
completion is polled with `xhci_event_poll`, and IE goes back up only once EP1 is
armed. One owner at every instant, and the transition is a single flag.

This does not weaken 5.1's claim. 5.1's NO-OP and its interrupt both run to
completion before any of this starts; 5.2 masks afterwards and re-arms at the
end, and the keystroke interrupts are a *new* claim, not a repeat of that one.

### 2. The ISR must clear IMAN.IP, or exactly one key works forever.

5.1's handler counts the message and retires it at the LAPIC. That is enough for
one interrupt. It is not enough for two: the interrupter's IP bit is
write-1-to-clear and the controller will not send another message while it is
set. A handler that leaves IP set gives exactly one keystroke and then silence —
and the gate would pass, because one keystroke is a keystroke.

**The gate therefore injects at least two keys**, and one of them carries a
modifier. A single-sample assertion is the shape that has already caught this
project out once, at M33.

### 3. PORTSC is written with a preserve mask, never read-modify-write.

PORTSC interleaves ordinary RW bits with RW1C change bits *and* with PED, which
is write-1-to-**disable**. Writing back what was read therefore disables the port
being reset and acknowledges every change nobody looked at.

Every write composes: keep PP and the other RW bits, write **zero** to PED and to
all of CSC/PEC/WRC/OCC/PRC/PLC/CEC, and set only the bit being asked for. Clearing
a change bit is a write of 1 to that bit alone, with PED and the rest at zero.

### 4. Context size comes from HCCPARAMS1.CSZ at run time, never from memory.

A context entry is `32 << CSZ` bytes. `xhci_csz()` already exists and is already
published. Nothing hardcodes 32.

DCI arithmetic is `ep * 2 + direction`, so **EP1 IN is DCI 3** — the doorbell
target, the Add Context flag A3, and the slot context's Context Entries all take
3, not 1.

### 5. The speed decode is an allowlist.

`usb-kbd` on `qemu-xhci` enumerates at **high speed** — measured, `info usb`
says 480 Mb/s — so EP0's Max Packet Size is 64 and the endpoint interval is
`bInterval - 1`. Full and low speed have different rules for both. Rather than
program a plausible wrong interval for a speed this has never seen, an
unrecognised speed is refused with a diagnostic, the same posture `array(n)`
takes towards a reference element type.

`bInterval` and `wMaxPacketSize` are read out of the configuration descriptor,
not assumed. That is standard descriptor walking, not HID report-descriptor
parsing, and it is the difference between a check and a hope.

## Memory

One more `pmm_alloc_contiguous` run, six pages, for the same reason 5.1 took one:
one physical base is one thing for the host to check, and page alignment already
satisfies every alignment the specification asks for here.

    +0  device context   (slot 1)
    +1  input context
    +2  EP0 transfer ring
    +3  EP1 transfer ring
    +4  descriptor buffer
    +5  HID report buffer   -- its own page, so the DMA target is trivially
                               addressable from outside the guest

## The gate

`-device usb-kbd,bus=xhci.0` alongside `qemu-xhci`, conditional on the same
`FK_MACHINE != pc` test. **It adds no PCI function** — it is a USB device on the
existing controller — so 4.2's `info pci` set comparison needs no change, which
was checked before anything was written.

Keys are injected with HMP `sendkey`, which `qmp-sentinel.py` already speaks.
Assertions come out of `fk_usbkbd_state` by `pmemsave` and off the device model
by `xp`, never off a line the kernel printed:

- the port that was reset, its speed, and PED set afterwards
- the slot id the controller assigned, and `DCBAA[slot]` holding the device
  context — read at its physical base
- the device context's **Slot State** as the controller wrote it: Addressed
  after Address Device, Configured after Configure Endpoint. That field is the
  controller's, not the kernel's, and it is the one thing here no kernel can fake.
- the eight bytes of each report, at the buffer's physical base
- the decoded characters, and `console_x` having advanced
- the transfer-event count, which must be **>= 2**

### One 5.1 assertion has to move

`check_xhci_rings` asserts `ERDP == evt_phys + 16` off the live device — exactly
one event consumed. Enumeration consumes many, so that becomes a comparison
against the dequeue index the guest publishes. Its self-test fixtures move with
it, and the mutation gets re-run.

## Mutations planned

Extending `tools/mutate-phase45.sh`. The ones that must refuse:

- port reset skipped
- PORTSC written read-modify-write (the PED trap)
- DCBAA slot entry never written
- Context Entries left at 1 when EP1 is added
- Add flag A3 not set on Configure Endpoint
- EP1 programmed as DCI 1 rather than 3
- doorbell rung at target 1 rather than 3
- **IMAN.IP not cleared in the ISR** — must produce exactly one key, which is why
  two are injected
- `SET_PROTOCOL` removed
- the modifier byte ignored

`SET_PROTOCOL` is called out because it may not be refutable: QEMU's keyboard
may report the same eight bytes in both protocols, in which case removing the
request changes nothing observable. That gets measured, and if it cannot be
refuted it is labelled QEMU-specific in `HARNESS-VALIDATION-PHASE5.md` rather
than counted as coverage — the same treatment as the CRCR read-back.
